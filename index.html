What it is

The premise

Most AI chat apps send every question — and whatever data answers it — to a hosted model behind an API key. This lab takes the cloud model away. A small open model runs on your machine through Ollama, and the data it talks about sits in a SQLite file beside it.

The model knows nothing about that data. It is not trained or fine-tuned on it. Every fact about a customer reaches it through a tool call, at the moment it is asked, so the data can change without retraining and every answer can be traced to a query.

The data belongs to Checkpoint Outfitters, a fictional adventure-racing gear shop. Three panes show the work: the chat, a live activity log down to the SQL, and a customer-service rep screen drawn from tool results — never from the model's own words. When the chat and the screen disagree, the screen is right.

The distinction the lab exists to make

What the model can reach is fixed by architecture: eight read-only tools, a database opened read-only, no SQL tool, no network. What it says is shaped by three guardrail layers, and those are weaker. The UI lets you switch each one off to see what it was stopping.

What's in it

Eight tools, three layers, one fictional shop

Eight read-only tools

ToolFor
find_customersSomeone by part of a name, email or phone
get_customerOne customer's full record
customer_segmentCustomers by place, join date, orders, spend, purchases — a filter required, no contact details for the model
list_ordersOrders by customer, status, dates, product, total, shipping state
get_orderOne order's lines and totals
find_productsThe catalogue by words, price, weight, colour, availability, sales history — sorted any way
get_productOne product with its sales figures
sales_reportA semantic layer: 6 metrics × 9 groupings, defined once in code

There is deliberately no SQL tool. When questions outgrew the narrow tools, the fix was flexible tools built from fixed SQL fragments the model picks by name — never SQL the model writes.

Three guardrail layers

LayerWhat it doesStrength
1 · Scoped promptTells the model its one jobSoft
2 · Structured repliesReply must be answer, clarify, unable or refuse; refusals show the app's wordsMedium
3 · Answer gateAn answer needs a successful lookup behind itMedium

The data

80 customers, 202 addresses, 120 products, 400 orders and 1,007 order lines, generated deterministically so every clone has the same shop. Deliberate edge cases: two customers with the same name, a customer with no orders, a product never ordered, a discontinued product in old orders, a seven-line order — and a product whose description carries a prompt injection.

Out of scope, deliberately

  • Writes — a guarded write tool with confirmation is the natural next lesson.
  • Streaming replies, and an input classifier as a fourth guardrail layer.

Running it

Five commands

Node 24, Ollama, and about 4 GB of memory for the model. Then: npm install, npm run seed, ollama pull qwen3.5:4b, npm run check-env, npm run dev — and open http://127.0.0.1:3200. No API key at any step.

Gotchas worth keeping

  • Setting format alongside tools stopped the model calling tools at all — it invented an order's contents instead.
  • Ollama silently drops older messages when a conversation outgrows num_ctx; the system prompt survives, a tool result may not.
  • Chat templates differ: llama3.2 removes the tool definitions from the prompt after the first tool result.
  • Qwen 3.5 thinks by default: 27 s for a one-word answer, 0.5 s with thinking off.
  • Tool wording becomes the model's answer: "contact details are not included" turned into "the records have no emails".

What this is for

All eight phases are complete and every figure on this page is measured. It is not production software — no authentication, localhost only, invented data. It is built to be read and watched.
